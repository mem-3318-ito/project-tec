# SLDS 静的 UI ルール

## アーキテクチャ

- `src/pages`: ページの構成のみ（15画面分を想定）。
- `src/components/common`: 全画面共通のパーツ。ヘッダー / グローバルナビゲーション / パンくずリスト / 戻るボタンの4種類のみとする。
- `src/components/[page]`: 画面・機能単位のUI単位（検索フォーム、テーブルなど）、およびLWCの境界線候補。全画面での共有は前提とせず、必要な画面ごとに個別実装する。
- `src/styles`: グローバルなベース/レイアウトに関する設定のみ。
- `dist`: 自動生成される出力ファイル。直接変更しないこと。
- Include（インクルード）のネストは浅く保つこと。最大2層までを目標とします。

## HTML

- 該当する場合はSLDS 2 Blueprintの構造を使用すること。
- セマンティックな要素（`button`、`a`、`nav`、`table`、`form`、見出し要素など）を使用すること。
- `label[for]` やARIA参照などのアクセシビリティ上の関連付けにおいては、`id` の使用を許可します。
- スタイル適用やJavaScriptの要素取得メカニズムとして `id` を使用しないこと。
- `iframe` を使用しないこと。
- インラインの `style` や、インラインの `on*` イベントハンドラーを使用しないこと。

## アクセシビリティ

- WCAG 2.1 AAへの準拠を到達目標とすること。
- 最低限、以下を確認すること: セマンティックHTML、`button`/`a`の適切な使い分け、`form`/`label`、見出し階層、`aria-*`属性、キーボード操作、フォーカス状態、エラー表示、必須項目表現、モーダルのフォーカス制御、タブ操作。
- SLDS 2 Blueprintにアクセシビリティ要件が記載されている場合は、それも遵守すること。

## CSS

- `.slds-*` をターゲットとするセレクターを作成しないこと。
- カスタムCSSを追加する前に、SLDSユーティリティクラスを優先して使用すること。
- プロジェクト独自のクラスには、可能な限り `app-{component}` および `app-{component}__{element}` を使用すること。
- コンポーネント固有のCSSは、該当コンポーネントの隣に配置すること。
- グローバルCSSにコンポーネント固有のスタイルを含めてはならない。

## JavaScript

- 最初にコンポーネントのルート要素を取得し、その後はそのルート内部のみをクエリ（要素検索）すること。
- DOMのフック（操作対象の識別）には `data-component`、`data-action`、`data-role` を使用すること。
- `getElementById` や `#id` によるクエリセレクターを使用しないこと。
- 振る舞いはプロトタイプとしての動作に留めること。ここでSalesforce API、認証、あるいはビジネスデータへのアクセスを実装しないこと。
- 検索とテーブルのように、コンポーネントを跨ぐ処理が必要な場合、コンポーネント同士が互いのDOMを直接操作しないこと。子コンポーネントは`CustomEvent`を発火するだけに留め、ページ側（または上位コンポーネント）がイベントを購読して仲介すること。

## 運用（Git / 品質担保）

- コード管理はBacklogのgit利用を想定しており、CIは利用できない前提とすること。
- Husky（pre-push）で `npm run check`（Lint一式 + Build）を自動実行し、Lint未通過のコードがpushされない構成にすること。
- PRレビューはUI/UXや表示・動作確認を中心に行うため、機械的に検出できる問題はpush前に解消しておくこと。

## LWC ハンドオフ（引き渡し）

- 静的コンポーネントは、可能な限り1つのLWCにマッピングできるようにすること。
- 静的実装はUI仕様のベースラインであり、LWC内部処理の再実装ではありません。
- LWCへの変換時は、適宜 Lightning Base Components（標準コンポーネント）を優先して使用すること。
- LWC化に伴うレンダリング上の差異は、静的ソースコードの不具合とは区別して扱うこと。
